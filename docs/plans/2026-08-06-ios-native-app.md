# The iOS half of the native app

## Context

`2026-08-05-capacitor-native-mobile.md` was written under a hard constraint: **iOS could not be
tested during development**, because development happened on Windows. Every platform decision it
made went through cross-platform Capacitor APIs for that reason, and CI compiled the iOS project on
a GitHub-hosted `macos-latest` runner so it could not silently rot.

That constraint is gone. Development moved to a Mac on 2026-08-06, and the iOS project was verified
compiling locally there — Xcode 26.6, `xcodebuild -sdk iphonesimulator`, **BUILD SUCCEEDED**. This
plan covers what the iOS half still needs, now that it can actually be run.

Two corrections to the earlier plan, both discovered during that verification:

- **CocoaPods is not involved, and never was.** This is Capacitor 8 on Swift Package Manager, and
  there is no Podfile in the repo. The earlier plan's "the only step needing macOS is `pod install`,
  and CI owns it" is wrong on both halves. `.github/workflows/native-build.yml` already says so in a
  comment on its `ios` job. Nothing here needs a Ruby toolchain.
- **`ios/App/CapApp-SPM/Package.swift` is a cross-platform tripwire.** It is tracked in git but
  generated by the Capacitor CLI, so it carries the path separators of whichever machine last ran
  `cap sync`. It arrived on the Mac with Windows separators (`..\..\..\node_modules\@capacitor\app`),
  which SPM cannot resolve — Xcode fails at package resolution with nothing pointing at the cause.
  CI never sees it, because the `ios` job runs `cap:sync` before `xcodebuild` and regenerates the
  file on the runner every time. **Recommendation: gitignore it.** CI regenerates it unconditionally,
  so nothing is lost, and the separator flip stops costing an hour the next time the two machines
  take turns.

## What is free, and what costs $99

The earlier plan grouped four iOS items under "when there is a Mac and a paid Apple Developer
account." That grouping is too coarse and has been holding up work that has no such dependency.

| Item | Needs paid enrolment? |
|---|---|
| iOS OAuth client → `environment.googleIosClientId` | **No** — a Google Cloud client keyed on the bundle ID |
| `GoogleService-Info.plist` | **No** — a Firebase console download |
| Running on the simulator, and on your own device | **No** — free provisioning, 7-day profiles |
| APNs auth key, Push Notifications entitlement | **Yes** |
| App Store / TestFlight distribution | **Yes** |

The bundle ID is `tv.groupspace.converge`, the same string as the Android `applicationId`.

## Part 1 — Google sign-in

`environment.ts` and `environment.development.ts` both carry `googleIosClientId: ''`, and the
comment there already records the design: native sign-in is handed the **web** client as its
`webClientId` and mints ID tokens with that as `aud`, so the backend verifies all three shells
against one client ID with no branching. The per-platform clients exist only so Google can attest
which app is asking. Android needs no ID in the environment at all — it is identified by package
name plus signing certificate — but iOS's Google Sign-In SDK requires its own client ID passed in.

So this is: create an iOS OAuth client for `tv.groupspace.converge` in the `groupspace-tv` project,
paste the ID into both environment files, and sign in on the simulator. No Apple account, no
entitlement, no backend change. It is the cheapest real progress available on iOS and should go
first.

## Part 2 — Push

Blocked on paid enrolment, and only on that. The backend's FCM send path is already shared —
`2026-08-05-fcm-electron-push-fix.md` built it that way deliberately, so that mobile would not mean
rebuilding it. What iOS adds is an APNs auth key uploaded to Firebase, `GoogleService-Info.plist` in
the app target, and the Push Notifications capability.

Worth noting the payoff is genuinely larger here than it was on desktop. The FCM plan's honest
ceiling for Electron was "notifications while the app is running," because no desktop OS has an
always-on push daemon. iOS does. This is where that investment actually lands.

## Part 3 — Screen share

The Android implementation is on `feature/android-screen-share` (~~not yet merged to `main` as of
this writing~~ — **wrong: it was already merged.** `a8e1ca1`, PR #113, 2026-08-06 10:36, four minutes
before this line was committed. Nothing to merge; the code is in `main`). Its shape:

```
MediaProjection → MediaCodec (H.264 Annex-B, baseline 3.1)
  → base64 chunks over the Capacitor bridge
  → WebCodecs VideoDecoder
  → MediaStreamTrackGenerator
  → an ordinary MediaStreamTrack, indistinguishable to MediaRoom from a getDisplayMedia one
```

It reaches for that path rather than a canvas for a stated reason: drawing frames ties the pipeline
to `requestAnimationFrame`, which stops when the app is backgrounded — and backgrounded is exactly
when the feature is used, since someone being talked through their phone is looking at Settings, not
at Converge.

**Both ends of that pipeline break on iOS, independently.**

### The native end: a broadcast extension is a separate process

Android's capture runs in a foreground service inside the app process, so the plugin can emit chunks
straight over the bridge. iOS has two capture APIs and they are not equivalent:

- `RPScreenRecorder.startCapture` runs in-process and is easy — but it captures **only the app's own
  content**. Useless for the actual use case.
- Whole-device capture requires a **Broadcast Upload Extension**, a second app target running in its
  own process, with a hard memory limit around 50MB, which cannot call the Capacitor bridge at all.

So iOS needs an IPC hop Android does not: extension → host app, via an App Group shared container,
a `CFMessagePort`, or Darwin notifications. Every one of those adds latency and a failure mode, and
the memory ceiling constrains how much can be buffered when the host app is not scheduled.

This is the same structural problem the earlier plan already flagged for the share target: "that
needs a Share Extension, which is a second app target rather than a file in this one." Two features
now want that machinery, which is an argument for building it once, deliberately.

### The web end: `MediaStreamTrackGenerator` is not in WebKit

> **CORRECTED 2026-08-08 — this section's conclusion is wrong, and so was the probe that "confirmed"
> it.** `MediaStreamTrackGenerator` is the DEPRECATED name and it is exposed in WORKER scope, not on
> `window`. The one-line check below tests `window.MediaStreamTrackGenerator` on the main thread,
> where it returns `undefined` on every platform including ones that fully support the feature — so
> it could not have detected the capability it was written to detect. WebKit ships the replacement,
> `VideoTrackGenerator`, and **it works on this app's own WKWebView on a physical iPhone.** See the
> 2026-08-08 section at the end. The web end does NOT break on iOS. The native end still does, for a
> different reason measured the same day.

WebKit bug 241124 — "Support Insertable Streams/MediaStreamTrackProcessor on Safari (both iOS and
MacOS)" — is still open. WKWebView therefore very likely has no `MediaStreamTrackGenerator`, which
is the exact API `native-screen-capture.ts` uses to turn decoded frames into a track. WebCodecs
itself has shipped in Safari since 16.4; it is specifically the track-generator half that is missing.

**This must be measured, not assumed, before any code is written.** The Android work set the right
standard here — it recorded `getDisplayMedia` as `undefined` on a Galaxy S10+ running Chrome 151
rather than reasoning about it. The equivalent check is one line in the WKWebView on a real device
and on the simulator:

```js
({MediaStreamTrackGenerator: typeof window.MediaStreamTrackGenerator, VideoDecoder: typeof window.VideoDecoder, EncodedVideoChunk: typeof window.EncodedVideoChunk})
```

**Measured 2026-08-06.** iPhone 17 Pro simulator, iOS 26.5, Safari Web Inspector attached to the
WKWebView of the debug build. Verbatim:

```
{MediaStreamTrackGenerator: "undefined", VideoDecoder: "function", EncodedVideoChunk: "function"}
typeof window.VideoEncoder  →  "function"
```

The prediction above holds: **the generator is absent, and WebCodecs is complete** — encode and
decode both present, exactly the split bug 241124 describes. The gap is not codec access; it is that
there is no way to hand a frame back to WebRTC as a track. Still to confirm on a real device, though
a WebKit feature flag is unlikely to differ from the simulator.

If the generator is genuinely absent, there are three ways out, in rising cost:

1. **Canvas + `captureStream()`.** The path Android rejected. `avatar-video-track.ts` already proves
   the codebase can publish a canvas-derived track. The backgrounding objection is *worse* on iOS,
   not better, so this only works if the use case is relaxed to foreground-only sharing — which
   guts most of its value.
2. **Publish natively.** Run the WebRTC send side for this one track in Swift, signalling through
   the existing socket. Correct and background-safe, but duplicates the signalling layer, and the
   extension's memory ceiling makes it harder than it sounds.
3. **Wait.** Ship iOS without screen share, exactly as the app ships today, and revisit when WebKit
   lands the generator. Not a regression: iOS Safari has no `getDisplayMedia` either.

**Recommendation: do not commit to an architecture until that one-line check has been run.** Parts 1
and 2 are unblocked and independent, and should not wait behind this.

## Part 4 — Share target

No iOS half exists. Needs a Share Extension — the second-app-target machinery from Part 3. Sequence
it after whichever of the two forces that decision first.

  dev backend over a real Let's Encrypt cert, which sidesteps it on iOS exactly as it does on

# 2026-08-08 — measured results

Everything below was measured on hardware or read out of source, not reasoned about. Where it
contradicts the plan above, the plan above is wrong and this section wins.

## Part 2 (Push) — mostly done, and cheaper than scoped

**Notification rendering and routing: DONE and verified**, without APNs. `xcrun simctl push` delivers
to the simulator with no token and no entitlement. All four paths confirmed on iPhone 17 Pro / iOS
26.5: foreground render (correct title/body/sound, tap routes to `/rooms/<name>?openChat=1` and lands
on the Chat tab); backgrounded OS-drawn notification and tap; **cold start** — app killed, tap,
routes correctly, so `consumePendingRoute()` works; and a control run proving a plain cold launch
lands on the room chooser, i.e. the above was routing and not state restoration.

Hand-testing note: the payload must be `data: { payload: "<json string>" }`, matching the backend's
`fcm.service.ts:54`. Fields at the top level of `data` are silently ignored by `parsePayload`, which
looks exactly like a broken app.

**Found while verifying: `dismiss-all` was a no-op on BOTH native platforms.** `push-sw.js` has
honoured it for the web all along; `native-push.ts` only early-returned, so a message read on one
device left its notification on every other one — precisely what `signalActive()` exists to prevent.
Fixed. **Live on Android** (`onMessageReceived` forwards data-only messages). **Still inert on iOS**:
`@capacitor/push-notifications` has no silent-push path there at all — it handles registration plus
VISIBLE notifications via the `UNUserNotificationCenter` delegate, and a `content-available` push
never reaches that delegate. `UIBackgroundModes: [remote-notification]` is necessary but NOT
sufficient; measured on the simulator, no JS listener fires with the key present. **Remaining work,
not enrolment-gated: an `AppDelegate.didReceiveRemoteNotification` forwarding into the bridge.**

**The APNs dependency question is resolved, and it shrinks this part.** `@capacitor-firebase/messaging@8.3.0`
declares `firebase-ios-sdk` in its own `Package.swift`, and Capacitor's generated manifest includes
every installed plugin as a local path package — so `npm i` + `cap sync` pulls Firebase in
transitively. The gitignored-`Package.swift` problem disappears rather than being worked around. The
plugin also already does `FirebaseApp.configure()` and sets `Messaging.messaging().apnsToken`, so
**a hand-written `FcmTokenPlugin.swift` and the AppDelegate wiring are not needed**; the
`FCM_TOKEN_PLUGIN` facade still is. `firebase` (the JS SDK) is an OPTIONAL peer dep, so no bundle cost.

Coexistence with `@capacitor/push-notifications` is safe — keep both. `registerForRemoteNotifications()`
is idempotent, and the APNs token reaches Firebase over NotificationCenter (a broadcast), so
`getToken()` depends on nothing push-notifications owns. **The one real conflict** is a single slot:
both assign `bridge.notificationRouter.pushNotificationHandler` in `load()`, last-writer-wins, and
Capacitor logs `"Push notification handler overriding previous instance"`. It governs only foreground
presentation and taps. Load order follows the generated `capacitor.config.json`, so watch for that
log line.

## Camera — DONE, zero code changes

iPhone SE (3rd gen), portrait capture: `photo-….jpg type=image/jpeg 2.29MB 3024x4032`. Both untested
assertions hold — JPEG not HEIC, and pixels genuinely rotated rather than EXIF-flagged.

## Part 3 (Screen share) — buildable now, but the expensive way

Three of this plan's blockers turned out not to be real, and the one that decides the cost was never
identified.

**Not blockers:**
- **Apple enrolment is NOT required.** App Groups, Keychain Sharing and Background Modes are
  available to free Apple Accounts, and a Broadcast Upload Extension needs no entitlement at all.
  Paid enrolment blocks push, TestFlight and distribution — not this.
- **`cap sync` will not fight a second app target.** The Capacitor CLI has no `pbxproj` handling
  outside opt-in `migrate` tasks; sync only rewrites gitignored files. The real constraint is
  narrower: the extension must never link `CapApp-SPM`, which is regenerated wholesale every sync.
- **The web end works.** On Clay's iPhone SE, in the app's own WKWebView: a worker-scope
  `VideoTrackGenerator` produced a live video track, transferred it to the main thread, and an
  `RTCPeerConnection` offer carried `m=video` with **VP8** — the codec the router requires.
  Main-thread readings were `VideoTrackGenerator=undefined MediaStreamTrackGenerator=undefined`,
  which is exactly why the original probe drew the wrong conclusion.

**The actual blocker: WKWebView stops executing when the app is backgrounded.** Measured on device
in the most favourable configuration that could ship — `audio` declared in `UIBackgroundModes` AND a
live mic stream held:

```
tick=34  dt=1010ms    workerFrames=33  visibility=hidden   ← backgrounded
tick=35  dt=42181ms   workerFrames=34  visibility=hidden   ← 42s elapsed, ONE tick, ONE frame
tick=36  dt=1005ms    workerFrames=35  visibility=visible  ← foregrounded
```

A 1s interval fired once in 42 seconds; the worker produced one frame instead of 42. Both the main
thread and the worker suspend.

That decides the architecture, and not for the reason this plan gives. Porting Android's pipeline
would work — the generator exists — but its second half runs inside this WebView, so it stops the
moment the user switches to the app they wanted to show. Foreground-only screen share means sharing
Converge back into Converge.

**So: Broadcast Upload Extension capturing via ReplayKit, with the WebRTC send side in Swift
(`mediasoup-client-swift` — SPM-native, WebRTC M140, ~10.9MB device slice), entirely in the extension
process.** Roughly 3–5 weeks. Scoped by measurement rather than by the guess this plan opened with.

Two further constraints for whoever builds it:
- **The router offers only Opus and VP8** (`room.service.ts:17-33`), and `recording.service.ts:1046`
  stream-copies to `.webm` because of it. Adding H.264 for iOS hardware encode is not free — it
  breaks recording.
- **One send transport per peer, keyed by `direction`.** A second `create-transport{send}` silently
  overwrites the slot and orphans the WebView's producers. Fixing this to key by id is ~1–1.5 days
  and also closes a latent transport leak.

Deliberately NOT measured: whether existing WebRTC audio/video keeps flowing while backgrounded.
That is handled below JS by WebKit and may well continue. The measurement above says only that
JavaScript stops — which is enough to kill any pipeline needing JS in the loop.
