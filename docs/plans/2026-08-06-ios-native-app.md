# The iOS half of the native app

## Context

`2026-08-05-capacitor-native-mobile.md` was written under a hard constraint: **iOS could not be
tested during development**, because development happened on Windows. Every platform decision it
made went through cross-platform Capacitor APIs for that reason, and CI compiled the iOS project on
a GitHub-hosted `macos-latest` runner so it could not silently rot.

That constraint is gone. Development moved to a Mac on 2026-08-06, and the iOS project was verified
compiling locally there — Xcode 26.6, `xcodebuild -sdk iphonesimulator`, **BUILD SUCCEEDED**. This
plan covers what the iOS half still needs, now that it can actually be run.

Two corrections to the earlier plan, both discovered during that verification:

- **CocoaPods is not involved, and never was.** This is Capacitor 8 on Swift Package Manager, and
  there is no Podfile in the repo. The earlier plan's "the only step needing macOS is `pod install`,
  and CI owns it" is wrong on both halves. `.github/workflows/native-build.yml` already says so in a
  comment on its `ios` job. Nothing here needs a Ruby toolchain.
- **`ios/App/CapApp-SPM/Package.swift` is a cross-platform tripwire.** It is tracked in git but
  generated by the Capacitor CLI, so it carries the path separators of whichever machine last ran
  `cap sync`. It arrived on the Mac with Windows separators (`..\..\..\node_modules\@capacitor\app`),
  which SPM cannot resolve — Xcode fails at package resolution with nothing pointing at the cause.
  CI never sees it, because the `ios` job runs `cap:sync` before `xcodebuild` and regenerates the
  file on the runner every time. **Recommendation: gitignore it.** CI regenerates it unconditionally,
  so nothing is lost, and the separator flip stops costing an hour the next time the two machines
  take turns.

## What is free, and what costs $99

The earlier plan grouped four iOS items under "when there is a Mac and a paid Apple Developer
account." That grouping is too coarse and has been holding up work that has no such dependency.

| Item | Needs paid enrolment? |
|---|---|
| iOS OAuth client → `environment.googleIosClientId` | **No** — a Google Cloud client keyed on the bundle ID |
| `GoogleService-Info.plist` | **No** — a Firebase console download |
| Running on the simulator, and on your own device | **No** — free provisioning, 7-day profiles |
| APNs auth key, Push Notifications entitlement | **Yes** |
| App Store / TestFlight distribution | **Yes** |

The bundle ID is `tv.groupspace.converge`, the same string as the Android `applicationId`.

## Part 1 — Google sign-in

`environment.ts` and `environment.development.ts` both carry `googleIosClientId: ''`, and the
comment there already records the design: native sign-in is handed the **web** client as its
`webClientId` and mints ID tokens with that as `aud`, so the backend verifies all three shells
against one client ID with no branching. The per-platform clients exist only so Google can attest
which app is asking. Android needs no ID in the environment at all — it is identified by package
name plus signing certificate — but iOS's Google Sign-In SDK requires its own client ID passed in.

So this is: create an iOS OAuth client for `tv.groupspace.converge` in the `groupspace-tv` project,
paste the ID into both environment files, and sign in on the simulator. No Apple account, no
entitlement, no backend change. It is the cheapest real progress available on iOS and should go
first.

## Part 2 — Push

Blocked on paid enrolment, and only on that. The backend's FCM send path is already shared —
`2026-08-05-fcm-electron-push-fix.md` built it that way deliberately, so that mobile would not mean
rebuilding it. What iOS adds is an APNs auth key uploaded to Firebase, `GoogleService-Info.plist` in
the app target, and the Push Notifications capability.

Worth noting the payoff is genuinely larger here than it was on desktop. The FCM plan's honest
ceiling for Electron was "notifications while the app is running," because no desktop OS has an
always-on push daemon. iOS does. This is where that investment actually lands.

## Part 3 — Screen share

The Android implementation is on `feature/android-screen-share` (not yet merged to `main` as of
this writing). Its shape:

```
MediaProjection → MediaCodec (H.264 Annex-B, baseline 3.1)
  → base64 chunks over the Capacitor bridge
  → WebCodecs VideoDecoder
  → MediaStreamTrackGenerator
  → an ordinary MediaStreamTrack, indistinguishable to MediaRoom from a getDisplayMedia one
```

It reaches for that path rather than a canvas for a stated reason: drawing frames ties the pipeline
to `requestAnimationFrame`, which stops when the app is backgrounded — and backgrounded is exactly
when the feature is used, since someone being talked through their phone is looking at Settings, not
at Converge.

**Both ends of that pipeline break on iOS, independently.**

### The native end: a broadcast extension is a separate process

Android's capture runs in a foreground service inside the app process, so the plugin can emit chunks
straight over the bridge. iOS has two capture APIs and they are not equivalent:

- `RPScreenRecorder.startCapture` runs in-process and is easy — but it captures **only the app's own
  content**. Useless for the actual use case.
- Whole-device capture requires a **Broadcast Upload Extension**, a second app target running in its
  own process, with a hard memory limit around 50MB, which cannot call the Capacitor bridge at all.

So iOS needs an IPC hop Android does not: extension → host app, via an App Group shared container,
a `CFMessagePort`, or Darwin notifications. Every one of those adds latency and a failure mode, and
the memory ceiling constrains how much can be buffered when the host app is not scheduled.

This is the same structural problem the earlier plan already flagged for the share target: "that
needs a Share Extension, which is a second app target rather than a file in this one." Two features
now want that machinery, which is an argument for building it once, deliberately.

### The web end: `MediaStreamTrackGenerator` is not in WebKit

WebKit bug 241124 — "Support Insertable Streams/MediaStreamTrackProcessor on Safari (both iOS and
MacOS)" — is still open. WKWebView therefore very likely has no `MediaStreamTrackGenerator`, which
is the exact API `native-screen-capture.ts` uses to turn decoded frames into a track. WebCodecs
itself has shipped in Safari since 16.4; it is specifically the track-generator half that is missing.

**This must be measured, not assumed, before any code is written.** The Android work set the right
standard here — it recorded `getDisplayMedia` as `undefined` on a Galaxy S10+ running Chrome 151
rather than reasoning about it. The equivalent check is one line in the WKWebView on a real device
and on the simulator:

```js
typeof window.MediaStreamTrackGenerator; typeof window.VideoDecoder;
```

If the generator is genuinely absent, there are three ways out, in rising cost:

1. **Canvas + `captureStream()`.** The path Android rejected. `avatar-video-track.ts` already proves
   the codebase can publish a canvas-derived track. The backgrounding objection is *worse* on iOS,
   not better, so this only works if the use case is relaxed to foreground-only sharing — which
   guts most of its value.
2. **Publish natively.** Run the WebRTC send side for this one track in Swift, signalling through
   the existing socket. Correct and background-safe, but duplicates the signalling layer, and the
   extension's memory ceiling makes it harder than it sounds.
3. **Wait.** Ship iOS without screen share, exactly as the app ships today, and revisit when WebKit
   lands the generator. Not a regression: iOS Safari has no `getDisplayMedia` either.

**Recommendation: do not commit to an architecture until that one-line check has been run.** Parts 1
and 2 are unblocked and independent, and should not wait behind this.

## Part 4 — Share target

No iOS half exists. Needs a Share Extension — the second-app-target machinery from Part 3. Sequence
it after whichever of the two forces that decision first.

## Explicitly out of scope

- App Store submission, review, and TestFlight. The Android side ships as a sideloaded APK and the
  iOS equivalent of that story does not exist; distribution is its own plan.
- The self-signed-CA-on-LAN problem. Native builds use the default environment and talk to the GCP
  dev backend over a real Let's Encrypt cert, which sidesteps it on iOS exactly as it does on
  Android.

## Open questions

- Is `MediaStreamTrackGenerator` present in WKWebView on a current iOS? Everything in Part 3 hangs
  off this.
- Is foreground-only screen sharing worth shipping on iOS if the generator is absent, or is no
  feature better than a misleading one?
- Should `Package.swift` be gitignored? Recommended above, but it is a repo-convention call.

## Verification

1. `npm test -- --watch=false` and `npm run build`, plus `npm run cap:sync` and a clean
   `xcodebuild -sdk iphonesimulator` — the same command CI runs.
2. Sign in with Google on the simulator once Part 1 lands, and confirm the backend accepts the token
   with no branching on `aud`.
3. On a real device, once enrolled: a push arriving with the app fully quit — the thing no desktop
   shell can do.
4. Nine locales for every new user-facing string, in the same commit. `locales.spec.ts` enforces it
   in both directions and will fail the build otherwise.
